# Backend integration guide

The application currently reads seeded data through `lib/api` and `lib/api/use-dataset.ts`; Zustand workspace state is a demo. It does not communicate with FastAPI, Supabase, GitHub, scanners or a security response platform. `lib/api/dataset.ts` and `lib/types/index.ts` describe current UI data, not an agreed backend schema.

`lib/integration/client.ts` provides an **unused** opt-in request transport. It accepts an externally configured base URL, an asynchronous access-token provider, and an active organization provider; it adds a bearer token and `X-Organization-Id` to relative requests, rejects cross-origin paths, checks HTTP status and supports abort signals. The header is a proposed integration convention, not an assertion that the backend supports it. Do not put service-role keys, Redis credentials or other privileged secrets in browser code. Production deployment should use HTTPS; define token storage and refresh with the authentication provider, and agree on CORS, error formats and session expiration.

Before connecting, agree and version request/response schemas and endpoint paths with the backend team. Needed capabilities include organization membership and selection, user/session and invitations, employee records and restricted HR cases, leave and promotion decisions, projects/tasks/sprints, PR and scanner integrations, financial data, incidents/telemetry/evidence, response approvals/reversals, notifications, search, audit and exports. Define pagination, filtering, idempotency, concurrency, errors and audit events for each. Validate responses at runtime; generic TypeScript types alone do not validate network data.

The server must authenticate each request, verify membership and object-level permissions for the requested organization, enforce sensitive-case access and state transitions, and record durable audit events. Never trust browser role, organization header or demo guards as authorization. Replace mock reads and store writes with adapters to agreed services, handle pending/error states and cancellation, invalidate or refetch dependent views after mutations, and test isolation using two real test tenants. Real provider actions require explicit authorization and should report actual success/failure; simulated operations must remain labeled until replaced.

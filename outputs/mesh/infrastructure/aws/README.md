# Authorized AWS role setup

`mesh-readonly-roles.json` is a reviewable CloudFormation template for a dedicated commercial-AWS sandbox account. It creates a posture role and, only when explicitly enabled, a separate billing role. No AWS resource has been deployed or queried here. The template contains no account credentials or invented tenant/account identifiers.

Supply the actual canonical MESH organization UUID and an existing trusted workload IAM role ARN as parameters. Trust is restricted to that exact source role; the template does not create source credentials, grant an account-root principal or trust a wildcard. CloudFormation assigns target role names. Review its change set with `CAPABILITY_IAM` before deployment. IAM permissions are security-sensitive infrastructure changes and require the operator's authorized AWS environment.

The posture allowlist matches the current collector's restricted session policy: bucket configuration/policy observations, security-group and RDS descriptions, IAM account/user/role/key/MFA and authorization-policy observations. It grants no S3 object reads, identity changes, policy attachment, credential creation, enforcement or response action. `Resource: "*"` covers the listed account inventory operations; it is not an action wildcard. Operator resource controls or organization policies can narrow access and produce explicit partial/denied coverage.

The optional billing role allows only `ce:GetCostAndUsage`. Cost Explorer activation, source-role authority and provider access policies are separate. Creating a role does not start MESH collection; the billing worker/profile and explicit finance-authorized request are required. Provider queries can incur charges. The backend fixes its query to the verified target role account, including when that is a management account; it does not authorize all consolidated accounts.

After reviewing/deploying in the selected account:

1. Give the source workload role `sts:AssumeRole` permission on the exact returned role ARN(s), subject to existing permission boundaries/SCPs. This template does not modify the source role or its credential chain.
2. Configure the actual output posture ARN in `AWS_ROLE_BINDINGS` for that MESH tenant, and the separate optional billing ARN in `AWS_BILLING_ROLE_BINDINGS`. Use protected runtime configuration; never tenant-supplied API credentials.
3. Supply the workload's authorized short-lived SDK credential chain/profile and supported `AWS_REGION`. Target session policies cannot grant permissions missing from the source/target role authority.
4. Run the controlled read-only inventory and billing comparisons in `docs/workstreams/R1_R4_LIVE_CONFIGURATION.md` and `R4_BILLING_COLLECTIONS.md`; retain denied/partial results honestly. Verify account/region/period/currency, cross-tenant denial, cancellation/revocation and replay without generating new paid requests automatically.

MESH requests 900-second STS sessions; the template's 3,600-second role maximum does not change that. Both adapters now send the canonical MESH organization UUID as `ExternalId`, and both template roles require the matching `sts:ExternalId` condition in addition to the exact workload principal. The backend validates the organization UUID before accessing the SDK credential chain and never retries a denied role without the external ID. This value is a tenant context identifier, not a password or substitute for source credentials. It is fixed by the backend tenant context rather than a collection request field. A custom existing trust policy that requires another external-ID value must be reviewed/migrated; MESH supplies no arbitrary API override.

Before accepting a real customer binding, verify that assumption succeeds with its correct external ID and fails with an omitted or another tenant's external ID. No such live trust-policy test was possible without authorized AWS credentials; local SDK fixtures do not prove the actual role policy enforces it. Source role deletion/recreation, principal changes and target binding changes require renewed review. Do not deploy this commercial-AWS example unchanged into GovCloud/China partitions or infer authorization from a tag. See [AWS external-ID guidance](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_common-scenarios_third-party.html) and [STS parameter constraints](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html).

Local validation checks JSON structure and action parity with the collector's SDK policy. AWS CloudFormation service validation, deployment, IAM evaluation and real collection acceptance remain pending authorized AWS access. Official reference: [CloudFormation IAM Role properties and outputs](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-iam-role.html).

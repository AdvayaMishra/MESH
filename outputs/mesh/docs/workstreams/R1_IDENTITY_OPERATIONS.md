# Identity-document operations preparation

This runbook describes existing technical controls and the deployment checks required before enabling production collection. It is not an organization approval, legal assessment or authorization to process a real person's documents. The user has deferred decisions requiring manual input.

Before enablement, the responsible organization must record the verification purpose, minimum necessary document content, authorized reviewers, collection notice, retention/hold policy, incident contact and approved evaluation criteria. The current implementation sets document expiry30days after upload; this is technical behavior, not a claim that30days is appropriate for every organization. Changes to that policy need explicit design/review rather than silently changing already-retained evidence.

Use fictional images for engineering checks. Production accuracy evaluation needs separately authorized representative data and criteria covering actual languages, layouts, quality variation, ambiguous/missing labels and incorrect nonempty extraction. The synthetic corpus scored9/10 name and10/10 employee-ID exact matches, including known-absent fields in the denominator. Its single name mismatch remains visible. OCR output is untrusted; neither extraction completion nor its score grants employee approval.

Uploads accept bounded validated PNG/JPEG images, up to2MiB and10million pixels. The malware gate must return a complete clean frame before upload can proceed. A detection rejects the content; unavailable, malformed, truncated, timed-out or certificate-invalid screening fails closed. Network screening has a20-second total budget with per-operation bounds. Set `CLAMAV_TLS=true` for a remote endpoint, use system roots or an explicit absolute CA file, and set the expected certificate DNS name only when necessary. There is no insecure-certificate fallback. Native clamd needs a TLS terminator when exposed remotely. Production plaintext is limited to an explicit loopback service/sidecar in the API host's network context.

The malware service operator must maintain signed signature updates, monitor their age/update failures, validate detections/outages using approved harmless test fixtures and restrict scanner access/logging. Configure the actual endpoint and monitoring before claiming deployment acceptance. A healthy socket or clean test verdict alone does not prove current signatures. These operational controls have not been accepted against a production service here.

Storage remains private, with exact tenant/employee/document object binding and stored content digest checks. Content is not made public or sent to an LLM. Access requires current authorized HR authority; organization ownership alone does not grant raw identity-document access. Signed content links last60seconds. Do not log document bytes, signed links, OTPs or native OCR text. Review all surrounding proxy/provider/support logging before real collection.

The OCR worker runs separately from the API using a trusted dedicated Linux launcher and a reviewed immutable image. Inference runs without network, host mounts or persistent container logs, as UID10001 with a read-only root and bounded resources/time. Results are encrypted with the independent document key and bound to the document/organization. Protect and retain keys while authorized records need decryption. Rotation requires a reviewed drain/re-encryption procedure; changing the sole key without one makes retained ciphertext unreadable. Invitation encryption uses a separate key.

The worker lease and fresh-authority checks prevent stale results being published after offboarding, expiry, HR decision or preservation changes. Independent HR must review the actual evidence before approval/rejection. Use the metadata-only review queue for triage; queue membership grants no extra content authority. Alert on failed/dead-letter jobs and unavailable screening/Storage/keys. Leave collection disabled while those dependencies are unaccepted.

Run the tenant-bound maintenance service, verify expiry/deletion and orphan reconciliation, and test failures/recovery on disposable fixtures. Preservation holds exclude retained bytes from normal deletion but do not extend expired content access. Hold release requires an independent reviewer; release does not automatically reactivate OCR or extend retention. Database holds do not restore already-missing bytes or prevent a separate Storage administrator from deleting objects. Storage administrator access, backups, retained keys and incident handling need explicit operational controls.

Before activation, run the production configuration gate with `--require-ocr`, review the matching fresh image assessment, confirm Storage/worker/malware authority, then complete representative controlled upload-to-review-to-expiry journeys on the actual deployment. The current image advisory gate remains failed; local TLS, fixture accuracy and retention tests do not override it. Record real evidence and cleanup with secrets and personal content excluded from public reports.

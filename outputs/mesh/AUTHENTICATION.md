# Authentication

## Observed refresh-reuse timing

Hosted probes used four distinct generations in one synthetic provider session. An ancestor token reused outside the configured10-second window was rejected with `refresh_token_already_used`. In an immediate follow-up within the provider reuse grace, the latest token was still accepted. An independent cohort that waited12seconds after the rejected ancestor reuse saw the latest token rejected too. Do not promise instantaneous provider-wide refresh-family invalidation from these results. Preserve the explicit MESH observed-session tombstone controls and account for the provider grace behavior in deployment review.

The mixed initial timing probe retains its failed immediate-revocation expectation; the later diagnostic and summary distinguish that observation from actual delayed rejection. An unconsumed administratively generated confirmation OTP was also rejected after a real605-second wait with the configured600-second expiry unchanged. No email was sent and all timed/diagnostic fixtures were removed. [Timed evidence](docs/timed-auth-acceptance-summary.json), [immediate diagnostic](docs/refresh-reuse-diagnostic-results.json), [post-grace diagnostic](docs/refresh-reuse-delayed-diagnostic-results.json). See [Supabase's documented session reuse exceptions](https://supabase.com/docs/guides/auth/sessions). The observed behavior is consistent with grace handling in the legacy refresh implementation; the hosted build version was not independently identified.

## Signup confirmation resend and OTP input

`POST /api/v1/auth/resend` accepts only `email` and `captcha_token`. It requests a signup confirmation resend through Supabase and returns HTTP 202 with a generic acknowledgment. It does not return tokens, change email addresses, create membership, choose arbitrary redirects or implement an independent OTP store. The CAPTCHA is forwarded to the provider. Login, registration, verification, recovery and resend share the same private per-account limiter; Redis failure denies the request. Supabase still controls actual eligibility, resend cooldown, CAPTCHA verification, expiration and replay detection.

`POST /api/v1/auth/verify` accepts 6–10 ASCII digits as a secret string, preserving leading zeroes, with type `signup` or `recovery`. Verification and recovery validate the email shape before contacting Supabase. Request validation responses omit sensitive input values. Successful OTP verification remains provider-owned; malformed or rejected provider sessions do not become MESH sessions.

Reviewable numeric-code templates live in `supabase/templates/confirmation.html` and `recovery.html`. They contain no authentication URLs, remote assets or executable content. They are source assets, not deployed provider settings. Provider resend contract: [Supabase resend](https://supabase.com/docs/reference/javascript/auth-resend).

Run `python scripts/verify_supabase_auth_policy.py` for a redacted read-only management configuration check. It requires `SUPABASE_ACCESS_TOKEN` in an operator environment and uses `SUPABASE_PROJECT_REF` or the configured hosted `SUPABASE_URL`. An optional `MESH_OPERATOR_ENV_FILE` names a protected operator file; existing environment values take precedence. It does not accept a secret as a command-line argument, follow redirects, print/store the raw config, change settings or send email. Exit 0 means the configuration baseline passed; exit 1 includes missing management authority, unavailable/invalid response, failed or unknown checks. The report is `docs/supabase-auth-policy-results.json`. Passing configuration checks never establishes live delivery or production clearance. See [R1 Auth acceptance](docs/workstreams/R1_AUTH_ACCEPTANCE.md).

Supabase Auth is the only credential authority. Configure email confirmation, short-lived numeric signup OTP templates, secure SMTP, CAPTCHA verification, OTP resend intervals/attempt caps, refresh reuse detection, password strength and privileged-user MFA in Supabase. Those controls are not automatically provided by application configuration.

`POST /api/v1/auth/register` forwards email/password/CAPTCHA to Supabase. `verify` exchanges email/token/type for provider-issued tokens. `login`, `refresh`, `recover` and `logout` proxy provider operations with bounded timeouts and generic errors. `PUT /auth/password` completes authenticated password changes/recovery. REQUIRE_PRIVILEGED_MFA enforces verified JWT aal2 for Owner/HR/Security Analyst and is mandatory in production configuration. Backend MFA and observed-session inventory/revocation routes are implemented below; client device hints are untrusted observations. Owner creates an organization only after successful email confirmation.

Bearer access tokens must use ES256 or RS256, match the configured issuer and `authenticated` audience, include subject/iat/exp, and resolve to a confirmed email through `/auth/v1/user`. HS256 compatibility mode is deliberately unsupported. Rotate Supabase asymmetric signing keys using provider JWKS. The key cache lives for five minutes; token expiry is checked on every request.

Tenant selection requires `X-Organization-ID`. Active membership and active organization status are checked on each request; the ID alone never grants access. Invitations may be accepted before membership exists, using the verified identity plus token, email binding, single-use row lock and selected organization. Organization registration bootstrap is the other membership-free operation.

The backend uses bearer tokens, not auth cookies, so it does not create a cookie/CSRF contract. A future frontend choosing cookies needs its own secure HttpOnly/Secure/SameSite and CSRF design. Do not store service-role keys in frontend code. Global logout revokes provider refresh sessions; access-token invalidation is bounded by token expiry. No claim of instant provider JWT revocation is made.

## Durable MESH session controls

Verified tokens now require a UUID session_id. Account-security metadata is self-owned with user-context RLS and is never exposed to an organization owner for another user. MESH immediately denies a revoked observed session across organization contexts, independent of token expiration. Revoke-one/revoke-others affect MESH observations; provider refresh revocation remains separate. Logout returns HTTP 200 with local count and provider confirmed/unavailable status; local revocation commits even when the provider is unavailable. Password changes revoke other observed MESH sessions. Current client hints are untrusted metadata; raw IPs, access tokens and refresh tokens are not stored in session rows. Tombstone retention and provider-wide session verification require operational privacy review before production.

## TOTP and session contract

The /api/v1/auth/mfa routes list factors, enroll TOTP, create a challenge, verify six-digit codes and remove an owned factor. Verification returns provider tokens; clients must replace their previous bearer token. Enrollment provisioning data is sensitive: never log it or insert provider SVG directly as executable markup. Supabase remains the factor authority. Removing a verified factor requires aal2 and revokes observed MESH sessions; sign in again. Logout returns HTTP 200 with mesh_sessions_revoked and provider_logout (confirmed/unavailable). Local session denial remains effective when provider logout fails; unseen provider sessions are outside the local ledger. Hosted provider acceptance now creates and removes a temporary Auth user and real TOTP factor; see docs/supabase-provider-results.json.

Provider references: [Supabase TOTP](https://supabase.com/docs/guides/auth/auth-mfa/totp), [factor enrollment](https://supabase.com/docs/reference/javascript/auth-mfa-enroll).

TOTP enrollment accepts provider QR SVG strings up to 1 MiB within a 1 MiB streamed response bound. Other provider Auth responses remain capped at 128 KiB. Do not insert SVG as executable markup or log provisioning secrets. The test machine clock was ahead of the provider; synthetic fixture code generation used HTTPS provider time. Keep deployment and authenticator clocks synchronized; production JWT verification was not relaxed.

Owner-name registration/profile support is implemented without a migration or second password store; see [display metadata contract](docs/workstreams/R1_OWNER_NAME.md). The temporary frontend keeps provider tokens in HttpOnly cookies through its local server bridge. Dedicated pre-confirmed test identities do not prove inbox/CAPTCHA/OTP production acceptance.
